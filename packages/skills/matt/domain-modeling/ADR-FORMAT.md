# ADR 格式

ADR 存放在 `docs/adr/` 中，并使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

延迟创建 `docs/adr/` 目录——仅在需要第一份 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、我们决定了什么，以及为什么。}
```

就是这样。一份 ADR 可以只有一个段落。其价值在于记录*做出了决策*以及*为什么做出决策*，而不是填满各个章节。

## 可选章节

只有在确实增加价值时才包含这些章节。大多数 ADR 不需要它们。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——在重新审视决策时很有用
- **考虑过的选项**——仅当被否决的替代方案值得记住时使用
- **后果**——仅当需要指出不明显的下游影响时使用

## 编号

扫描 `docs/adr/`，找到现有的最大编号并加一。

## 何时提供 ADR

以下三点必须同时成立：

1. **难以逆转**——日后改变想法的代价很大
2. **脱离上下文会令人意外**——未来的读者看到代码会疑惑“为什么偏偏要这样做？”
3. **源于真正的权衡**——确实存在替代方案，而你基于具体原因选择了其中一个

如果一个决策很容易逆转，就跳过它——你只会再次逆转。如果它不令人意外，就没人会疑惑为什么。如果不存在真正的替代方案，除了“我们做了显而易见的事情”之外，没有什么可记录的。

### 哪些情况符合条件

- **架构形态。**“我们使用 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。**“Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。”
- **会造成锁定的技术选择。**数据库、消息总线、身份验证提供商、部署目标。不是每个库，而是那些替换需要花费一个季度的组件。
- **边界和范围决策。**“Customer 数据由 Customer 上下文所有；其他上下文只能通过 ID 引用它。”明确的否定和肯定同样有价值。
- **对显而易见路径的刻意偏离。**“我们使用手写 SQL 而不是 ORM，因为 X。”任何合理的读者都会以为应该相反的情况，都值得记录。这可以阻止下一位工程师“修正”一个本来就是刻意为之的做法。
- **代码中不可见的约束。**“由于合规要求，我们不能使用 AWS。”“由于合作方 API 合同要求，响应时间必须低于 200ms。”
- **被否决的替代方案，且否决原因并不明显。**如果你考虑过 GraphQL，却因微妙的原因选择了 REST，就记录下来——否则六个月后又会有人提议 GraphQL。
