# 领域建模

在设计时主动构建并完善项目的领域模型。这是一项*主动的*工作——质疑术语、构想边界情况，并在术语表和决策逐渐明确的当下将它们记录下来。（仅仅为了获取词汇而*阅读* `CONTEXT.md` 不属于这项 skill——任何 skill 都能做到这一行习惯。这项 skill 用于修改模型，而不只是使用模型。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `CONTEXT-MAP.md`，则仓库包含多个上下文。该映射会指出每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统范围的决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

延迟创建文件——仅在有内容需要写入时创建。如果不存在 `CONTEXT.md`，就在解析出第一个术语时创建。如果不存在 `docs/adr/`，就在需要第一份 ADR 时创建。

## 会话期间

### 对照术语表进行质疑

当用户使用的术语与 `CONTEXT.md` 中现有的语言冲突时，立即指出来。“你的术语表将 ‘cancellation’ 定义为 X，但你似乎指的是 Y——到底是哪一个？”

### 让模糊的语言变得精确

当用户使用含糊或含义过多的术语时，提出一个精确的规范术语。“你说的是 ‘account’——你指的是 Customer 还是 User？它们是不同的概念。”

### 讨论具体场景

讨论领域关系时，用具体场景进行压力测试。构想探查边界情况的场景，迫使用户明确概念之间的边界。

### 与代码交叉核对

当用户陈述某件事的工作方式时，检查代码是否一致。如果发现矛盾，就指出来：“你的代码会取消整个 Order，但你刚才说可以部分取消——哪个说法才对？”

### 内联更新 CONTEXT.md

术语确定后，立即更新 `CONTEXT.md`。不要批量处理——在术语确定时就记录下来。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不包含实现细节。不要把 `CONTEXT.md` 当作规范、草稿或实现决策的存放处。它就是术语表，仅此而已。

### 谨慎提供 ADR

只有以下三点同时成立时，才提议创建 ADR：

1. **难以逆转**——日后改变想法的代价很大
2. **脱离上下文会令人意外**——未来的读者会疑惑“为什么要这样做？”
3. **源于真正的权衡**——确实存在替代方案，而你基于具体原因选择了其中一个

如果缺少其中任何一点，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
