# 诊断 Bug

针对难查 Bug 的纪律。只有明确说明理由时才能跳过阶段。

探索代码库时，读取 `CONTEXT.md`（若存在）以建立相关模块的清晰心智模型，并检查所改区域的 ADR。

## 脱敏

本技能要求展示命令、输出和捕获的产物。**先将所有密钥脱敏**，用 `<REDACTED>` 替换。围绕环境变量建立闭环，使凭据留在环境中，而不是出现在展示内容里。捕获的产物含有认证请求头；只引用承载有效信号的行。

如果脱敏后的输出不足以诊断 Bug，明确说明并询问用户。

## 阶段 1——建立反馈闭环

**这就是本技能。** 其他一切都是机械步骤。只要拥有一个能在这个 Bug 上变红的**紧密**通过/失败信号，你就能找到原因；二分、假设检验和插桩都只是在消费这个信号。没有它，再怎么盯代码也无济于事。

在这里投入不成比例的精力。**积极尝试。发挥创造力。拒绝放弃。**

### 构造闭环的方法——大致按以下顺序尝试

1. 在任何能触达 Bug 的接缝处编写**失败测试**——单元、集成或端到端。
2. 对运行中的开发服务器使用 **Curl / HTTP 脚本**。
3. 用夹具输入执行 **CLI 命令**，将 stdout 与已知正确的快照比较。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，并断言 DOM、console 或 network。
5. **重放捕获的轨迹。** 将真实网络请求、payload 或事件日志保存到磁盘，在隔离环境中通过代码路径重放。
6. **一次性夹具。** 启动系统的最小子集（一个服务、模拟依赖），通过一次函数调用触发 Bug 路径。
7. **属性 / 模糊测试循环。** 如果 Bug 是“输出偶尔错误”，运行 1000 个随机输入寻找失败模式。
8. **二分夹具。** 如果 Bug 出现在两个已知状态（commit、数据集、版本）之间，自动执行“在状态 X 启动、检查、重复”，以便运行 `git bisect run`。
9. **差分闭环。** 用同一输入运行旧版与新版（或两份配置），比较输出。
10. **HITL Bash 脚本。** 最后手段。必须由人点击时，用 `scripts/hitl-loop.template.sh` 引导其操作，使闭环仍保持结构化；捕获的输出返回给你。

建立正确的反馈闭环，Bug 就修好了 90%。

### 收紧闭环

把闭环当作产品。有了闭环后，继续**收紧**它：

- 能否更快？（缓存准备工作、跳过无关初始化、缩小测试范围。）
- 信号能否更锐利？（断言具体症状，而不是“没有崩溃”。）
- 能否更确定？（固定时间、设置随机种子、隔离文件系统、冻结网络。）

30 秒的 flaky 闭环几乎不比没有好；2 秒的确定性闭环才算紧密——这是调试的超能力。

### 非确定性 Bug

目标不是干净复现，而是提高复现率。循环触发 100 次、并行执行、增加压力、缩窄时序窗口、注入 sleep。50% 复现率的 flaky Bug 可以调试；1% 不行——继续提高，直到可调试。

### 确实无法建立闭环时

停止并明确说明。列出尝试过的方法。向用户请求：(a) 可复现环境的访问权限，(b) 已脱敏的捕获产物（HAR、日志 dump、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的权限。没有闭环时**禁止继续提出假设**。

### 完成标准——一个会变红的紧密闭环

阶段 1 完成时，你能说出**一条已经至少运行过一次的命令**——脚本路径、测试命令或 curl——展示其脱敏后的调用和输出，并且它满足：

- [ ] **能变红**——运行真实 Bug 路径并断言用户的**准确症状**，因此能在该 Bug 上变红、修复后变绿。仅仅“运行没报错”不算；它必须能抓住这个具体 Bug。
- [ ] **确定**——每次运行结论一致；flaky Bug 则按上文固定到较高复现率。
- [ ] **快速**——耗时是秒级，不是分钟级。
- [ ] **Agent 可运行**——可以无人值守运行；只有确实无法避免时，才通过 `scripts/hitl-loop.template.sh` 让人参与。

如果发现自己在这条命令存在之前就阅读代码、建立理论，**立即停止——直接跳到假设正是本技能要防止的失败。** 没有能变红的命令，就不能进入阶段 2。

## 阶段 2——复现并最小化

运行闭环，看它变红——Bug 出现。

确认：

- [ ] 闭环产生的是**用户**描述的失败模式，而不是附近另一个不同失败。Bug 错了，修复就会错。
- [ ] 多次运行均可复现；对于非确定性 Bug，复现率足够高，可以据此调试。
- [ ] 已捕获准确症状（错误信息、错误输出、耗时），后续阶段才能确认修复确实命中它。

### 最小化

闭环变红后，把复现缩减成**仍会变红的最小场景**。每次只删除一个输入、调用方、配置、数据或步骤，并重新运行闭环；只保留支撑失败的元素。

这样做是因为最小复现会缩小阶段 3 的假设空间，并在阶段 5 成为干净的回归测试。

当**每个剩余元素都不可或缺**——删除任意一个都会让闭环变绿——才算完成。

复现并最小化之前不要继续。

## 阶段 3——提出假设

测试前生成 **3–5 个排序后的假设**。只生成一个会让你锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说明它会做出什么预测。

> 格式：“如果 `<X>` 是原因，那么 `<改变 Y>` 会让 Bug 消失 / `<改变 Z>` 会让它更严重。”

无法陈述预测的假设只是感觉——丢弃或收紧。

**测试前向用户展示排序列表。** 用户通常掌握能立即调整顺序的领域知识（“我们刚部署了与 #3 相关的改动”），或知道哪些假设已被排除。这是成本很低、收益很高的检查点。不要因此阻塞；用户不在场时按你的排序继续。

## 阶段 4——插桩

每个探针必须对应阶段 3 的一个具体预测。**一次只改变一个变量。**

工具优先级：

1. 环境支持时使用 **Debugger / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界处添加**定向日志**。
3. 禁止“把一切都打日志再 grep”。

每条调试日志都用唯一前缀标记，例如 `[DEBUG-a4f2]`。结束时一次 grep 即可清理。未标记的日志会残留；标记过的必须删除。

**性能分支。** 对性能回归，日志通常是错误工具。应先建立基线测量（计时夹具、`performance.now()`、profiler、query plan），再二分。先测量，再修复。

## 阶段 5——修复并添加回归测试

在修复前编写回归测试——但前提是存在**正确的接缝**。

正确接缝会按 Bug 在调用点真实发生的模式执行测试。如果唯一可用的接缝太浅（Bug 需要多个调用方，但测试只有一个；单元测试无法复现触发 Bug 的调用链），这里的回归测试会提供虚假信心。

**没有正确接缝本身就是一项发现。** 记录下来：代码库架构正在阻止这个 Bug 被锁定，并在下一阶段标记它。

存在正确接缝时：

1. 将最小复现转成该接缝上的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始、未最小化的场景重新运行阶段 1 的反馈闭环。

## 阶段 6——清理与复盘

宣布完成前必须满足：

- [ ] 原始复现不再出现（重跑阶段 1 的闭环）
- [ ] 回归测试通过（或已记录缺少正确接缝）
- [ ] 所有 `[DEBUG-...]` 插桩已删除（grep 该前缀）
- [ ] 一次性原型已删除，或移动到明确标记的调试位置
- [ ] 最终成立的假设写入 commit 或 PR 消息，让下一位调试者能够学习
