# 转为工单

将计划、规格说明或对话拆分为一组 **工单**——tracer-bullet 垂直切片，每个工单都声明会 **阻塞** 它的工单。

问题跟踪器和分诊标签词汇应已提供给你；如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。如果用户将引用（规格说明路径、问题编号或 URL）作为参数传入，请获取并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果尚未探索代码库，请先这样做，以了解代码的当前状态。工单标题和描述应使用项目领域术语表中的词汇，并遵循你正在修改区域的 ADR。

寻找预先重构代码的机会，以便让实现更容易。“先让改动变容易，再完成这个容易的改动。”

### 3. 起草垂直切片

将工作拆分为 **tracer bullet** 工单。

<vertical-slice-rules>

- 每个切片都要贯穿每一层，形成一条窄而 COMPLETE 的路径（schema、API、UI、tests）——是垂直切片，NOT 某一层的水平切片
- 完成的切片应能独立演示或验证
- 每个切片的规模应适合放入一个全新的上下文窗口
- 任何预先重构都应首先完成

</vertical-slice-rules>

为每个工单标明其 **阻塞边**——必须先完成、工单才能开始的其他工单。没有阻塞项的工单可以立即开始。

**大范围重构是垂直切片的例外。** **大范围重构** 是一次机械性改动——重命名列、重新定义共享符号类型——其 **影响范围** 扩散到整个代码库，因此单次编辑会同时破坏数千个调用点，任何垂直切片都无法以绿色状态合入。不要强行将它拆成 tracer bullet；应按 **expand–contract** 排序。首先 expand：在旧形式旁边添加新形式，确保不破坏任何内容。然后按影响范围分批迁移调用点（每个包、每个目录一批），每批作为独立工单并受 expand 阻塞；由于旧形式仍然存在，各批次之间都能保持 CI 绿色。最后 contract：在没有调用方后删除旧形式，创建一个受所有迁移批次阻塞的工单。当即使这些批次也无法独立保持绿色时，仍保留这个顺序，但让它们共享一个集成分支，并全部阻塞最后的 integrate-and-verify 工单——只有在那里才承诺绿色。

### 4. 询问用户

用编号列表呈现拟议的拆分。对每个工单展示：

- **标题**：简短的描述性名称
- **阻塞于**：必须先完成的其他工单（如有）
- **交付内容**：该工单使之可用的端到端行为

询问用户：

- 粒度是否合适？（过粗 / 过细）
- 阻塞边是否正确——每个工单是否只依赖真正构成门槛的工单？
- 是否应合并某些工单，或进一步拆分？

持续迭代，直到用户批准这份拆分。

### 5. 将工单发布到已配置的跟踪器

先按跟踪器的发布前查重约定处理与他人工单的重叠，再发布已批准的工单。**方式**取决于配置的跟踪器——无论采用哪种方式，工单都相同，只有阻塞边的表现形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单写入一个文件，按依赖顺序从 `01` 开始编号（阻塞项优先）。每个文件的“阻塞于”列出它所依赖的编号/标题。使用下面的单工单文件模板——每个文件一个工单，绝不能写成单个合并文件。
- **真实问题跟踪器（GitHub、Linear、……）** → 按依赖顺序为每个工单发布一个问题（阻塞项优先），以便每个工单的阻塞边可以引用真实标识符。跟踪器支持时使用其原生阻塞 / 子问题关系；否则将每个工单的“阻塞于”设为阻塞问题。除非另有指示，否则应用 `ready-for-agent` 分诊标签（实际字符串见分流标签表）——这些工单按其设计即可由代理领取。

处理 **前沿**：所有阻塞项都已完成的任何工单。对于纯线性链，这意味着从上到下。

不要关闭或修改任何父问题。
