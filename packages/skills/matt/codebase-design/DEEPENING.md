# 深化模块

在给定依赖关系的情况下，如何安全地深化一组浅模块。假定使用 [SKILL.md](SKILL.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估深化候选对象时，先对其依赖进行分类。类别决定了如何跨其接缝测试深化后的模块。

### 1. 进程内

纯计算、内存中的状态、无 I/O。始终可以深化——合并模块，并直接通过新接口测试。不需要适配器。

### 2. 可在本地替代

具有本地测试替代物的依赖（用于 Postgres 的 PGLite、内存文件系统）。如果替代物存在，就可以深化。深化后的模块使用测试套件中运行的替代物进行测试。接缝是内部的；模块的外部接口处不需要端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议形式：*“在接缝处定义一个端口，为生产环境实现 HTTP 适配器、为测试实现内存适配器，这样即使逻辑跨网络部署，也能放在一个深模块中。”*

### 4. 真正的外部依赖（模拟）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的端口；测试提供模拟适配器。

## 接缝纪律

- **一个适配器意味着假设性的接缝，两个适配器意味着真实的接缝。** 除非至少有两个适配器有充分理由存在（通常是生产环境 + 测试），否则不要引入端口。只有一个适配器的接缝只是间接层。
- **内部接缝与外部接缝。** 深模块可以有内部接缝（实现私有、由自身测试使用），也可以有位于其接口处的外部接缝。不要仅仅因为测试使用内部接缝，就通过接口暴露它们。

## 测试策略：替换，不要叠加

- 浅模块上的旧单元测试，在深化后的模块接口已经存在测试后就成为负担——删除它们。
- 在深化后的模块接口处编写新测试。**接口就是测试面。**
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应能经受内部重构——它们描述的是行为，而不是实现。如果实现变化就必须修改测试，那么测试测试的就是接口之外的内容。
