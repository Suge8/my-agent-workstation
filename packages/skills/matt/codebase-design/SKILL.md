# 代码库设计

设计**深模块**：让大量行为隐藏在小接口之后，放置于清晰的接缝上，并通过该接口进行测试。在设计或重构代码的任何地方都使用这套语言和这些原则。目标是为调用方提供杠杆效应，为维护者提供局部性，并让所有人都能进行测试。

## 术语表

请严格使用这些术语——不要替换为“组件”“服务”“API”或“边界”。一致的语言是全部要点。

**模块（Module）**——任何具有接口和实现的事物。有意保持与规模无关：函数、类、包或跨层切片。_避免使用_：单元、组件、服务。

**接口（Interface）**——调用方必须知道的、用于正确使用模块的一切：类型签名，以及不变量、顺序约束、错误模式、必需配置和性能特征。_避免使用_：API、签名（范围过窄——它们只指类型层面的表面）。

**实现（Implementation）**——模块内部的内容，即代码主体。它不同于**适配器（Adapter）**：一个事物可以是实现很大的小适配器（Postgres 仓库），也可以是实现很小的大适配器（内存伪实现）。当主题是接缝时使用“适配器”，否则使用“实现”。

**深度（Depth）**——接口上的杠杆效应：调用方（或测试）每学习一个单位的接口，就能使用的行为量。当大量行为隐藏在小接口之后时，模块是**深的**；当接口几乎和实现一样复杂时，模块是**浅的**。

**接缝（Seam）**（Michael Feathers）——可以在不修改该处的情况下改变行为的位置；也就是模块接口所在的*位置*。接缝放在哪里是独立的设计决策，不同于接缝背后放什么。_避免使用_：边界（与 DDD 的限界上下文含义冲突）。

**适配器（Adapter）**——在接缝处满足接口的具体事物。描述的是**角色**（它填补什么位置），而不是实质（内部是什么）。

**杠杆效应（Leverage）**——调用方从深度中获得的东西：每学习一个单位的接口，就能获得更多能力。一个实现可以在 N 个调用点和 M 个测试之间摊还成本。

**局部性（Locality）**——维护者从深度中获得的东西：变更、缺陷、知识和验证集中在一个地方，而不是扩散到调用方。修复一次，处处修复。

## 深模块与浅模块

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 少量方法、简单参数
├─────────────────────┤
│                     │
│      深实现         │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│          大接口                 │  ← 许多方法、复杂参数
├─────────────────────────────────┤
│          薄实现                 │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 能否减少方法数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂性？

## 原则

- **深度是接口的属性，而不是实现的属性。** 深模块的内部可以由小型、可模拟、可替换的部分组成——只是它们不属于接口。模块可以有**内部接缝**（实现私有、由自身测试使用），也可以有位于其接口处的**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂性随之消失，它就是透传层。如果复杂性在 N 个调用方之间重新出现，它就发挥了应有的价值。
- **接口就是测试面。** 调用方和测试跨越的是同一个接缝。如果你想越过接口测试，模块可能就不是正确的形状。
- **一个适配器意味着假设性的接缝，两个适配器意味着真实的接缝。** 除非确实有东西会在接缝两侧变化，否则不要引入接缝。

## 面向可测试性设计

好的接口会让测试变得自然：

1. **接收依赖，不要创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **保持表面小巧。** 方法越少，需要的测试就越少。参数越少，测试设置就越简单。

## 关系

- 一个**模块（Module）**恰好有一个**接口（Interface）**（它呈现给调用方和测试的表面）。
- **深度（Depth）**是**模块（Module）**的属性，根据其**接口（Interface）**衡量。
- **接缝（Seam）**是**模块（Module）**的**接口（Interface）**所在的位置。
- **适配器（Adapter）**位于**接缝（Seam）**处并满足**接口（Interface）**。
- **深度（Depth）**为调用方产生**杠杆效应（Leverage）**，为维护者产生**局部性（Locality）**。

## 被否定的表述

- **将深度视为实现行数与接口行数之比**（Ousterhout）：这会奖励填充实现。我们使用“作为杠杆效应的深度”。
- **将“接口”视为 TypeScript 的 `interface` 关键字或类的公共方法**：范围过窄——这里的接口包含调用方必须知道的每一项事实。
- **“边界”**：与 DDD 的限界上下文含义冲突。请说**接缝**或**接口**。
