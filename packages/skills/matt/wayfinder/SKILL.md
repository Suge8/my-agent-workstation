一个模糊的想法出现了——它对单个 agent 会话来说太大，又笼罩在迷雾中：从这里到 **目的地** 的路还看不见。寻路的目标是找到这条路，而不是冲向目的地。这项 skill 会在仓库的 **issue tracker** 上将路径绘制成一张**共享地图**，然后逐一处理它的**决策工单**——这些问题的解决结果是一个决定，而不是可直接执行的构建切片——直到路线清晰为止。

每项工作的目的地各不相同，而命名目的地是绘图的第一步——它会塑造每一张工单。目的地可能是一份要交接并迭代的规格说明、一项必须在开始规划前锁定的决定，或是一项原地完成的变更，例如数据结构迁移。这张地图与领域无关——工程工作、课程内容，任何符合这种形态的事情都可以。

## 规划，不要执行

Wayfinder 默认是**规划**：每张工单解决一个决定，当路径清晰时地图就完成了——在有人去执行之前，不再有任何待决定事项。想直接开始做工作的冲动，通常意味着你已经走到了地图边缘，现在该交接了。某项工作可以在它的 **Notes** 中覆盖这一默认行为——把执行也纳入地图本身——但除此之外，产出决定，而不是交付物。

## 按名称引用

每张地图和每张工单都是一个 issue，因此都有一个**名称**——也就是标题。在人类会阅读的所有内容中——叙述、地图的 Decisions-so-far——都按名称引用它，绝不要只使用裸 id、编号或 slug。满屏的 `#42, #43, #44` 无法阅读；名称一眼就能看懂。id 和 URL 不会消失——名称会包裹它们的链接——但它们位于名称**内部**，绝不能代替名称。

## 地图

地图是这个仓库 issue tracker 上的单个 issue，标签为 `wayfinder:map`——这是规范产物。它的工单是地图的子 issue。

地图是一个**索引**，不是存储区。它列出已作出的决定，并指向保存详细内容的工单；一个决定只存在于一个地方——它自己的工单——因此地图不会重述它，只会概述并链接。

**地图、子工单、阻塞关系以及 frontier 查询在物理上位于何处，取决于 tracker。** 你应该已经获得 issue tracker；如果没有，请告知用户运行 `/setup-matt-pocock-skills`。查阅 tracker 文档中的 “Wayfinding operations” 部分，了解**这个**仓库如何表达这些操作。如果没有提供 tracker，默认使用本地 Markdown tracker。

### 地图正文

每次会话加载一次的低分辨率完整地图。未关闭的工单**不会**列出——它们是通过查询找到的开放子 issue。

```markdown
## Destination

<到达这张地图终点的样子——这项工作正在寻找的规格、决定或变更。一到两行；每个会话在选择工单前都要据此定位。>

## Notes

<领域；每个会话都应查阅的 skills；这项工作的长期偏好>

## Decisions so far

<!-- 索引——每个已关闭工单一行：足以判断相关性，然后打开链接查看工单保存的详细内容 -->

- [<closed ticket title>](link) — <one-line gist of the answer>

## Not yet specified

<!-- 参见“Fog of war”：范围内尚无法建立工单的迷雾；随着 frontier 推进而转为明确内容 -->

## Out of scope

<!-- 参见“Out of scope”：已排除在目的地之外的工作；关闭，永不转为明确内容 -->
```

### 工单

每张工单都是地图的**子 issue**；tracker 的 issue id 是其身份。其正文是一个问题，规模控制在单个 100K token agent 会话内：

```markdown
## Question

<这张工单要解决的决定或调查>
```

每张工单都带有一个 `wayfinder:<type>` 标签，类型取 `research`、`prototype`、`grilling`、`task` 之一（见 [Ticket Types](#ticket-types)）。

一个会话在开始任何工作**之前**先通过将工单分配给推动地图前进的 dev 来“认领”工单，这样并行会话就会跳过它。那个受分配者就是认领状态：开放且未分配的工单尚未被认领。

阻塞使用 tracker 的**原生**依赖关系——这很重要，因为它会在 tracker 自己的 UI 中以可视方式呈现 frontier，让人无需打开地图就能看到哪些工单可取。只有不具备原生阻塞关系的 tracker 才退回使用正文约定。当阻塞它的每张工单都已关闭时，工单才是**未阻塞**的；**frontier** 是开放、未阻塞、未认领的子工单——已知范围的边缘。

答案不属于正文——它会在解决时记录（见 [Work through the map](#work-through-the-map)）。解决工单时创建的资产要从 issue 链接，而不是粘贴进去。

## 工单类型

每张工单都属于 **HITL**——有人参与，由代表自己发言的人共同完成——或 **AFK**——完全由 agent 独立推动。HITL 工单只能通过实时交流解决；agent 绝不能代替人类完成其一方（会自己回答自己问题的 grilling agent 就违反了这一点）。

- **Research**（AFK）：阅读文档、第三方 API 或知识库等本地资源，找出某项决定所依赖的事实。由使用 `research` skill 的 **subagent** 解决。需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：通过制作一个便宜、粗略、具体的可反馈资产——大纲、粗略方案、存根，或通过 `prototype` skill 编写的 UI/逻辑代码——提高讨论的保真度。将原型作为资产链接。关键问题是“应该长什么样”或“应该如何表现”时使用。
- **Grilling**（HITL）：对话。默认情况。始终使用 `grilling` 和 `domain-modeling` 两个 skill。
- **Task**（HITL 或 AFK）：在作出**决定**之前必须完成的手工工作——没有什么需要决定、制作原型或研究，但讨论被它阻塞。例如注册服务以评估其 API、配置访问权限、移动数据以观察其形态。这是唯一一个确实“执行”而非作出决定的类型——它之所以值得存在，是因为它解除了一个决定的阻塞，而不是因为它交付了目的地。能独立完成的部分由 agent 独自推动（AFK）；否则向人类交付精确的检查清单（HITL）。工作完成时解决；答案记录已完成的工作及由此得到的事实（凭据位置、新 URL、行数等），供后续工单依赖。

## 战争迷雾

地图是**刻意**不完整的：不要绘制尚且看不见的内容。当前工单之外是**战争迷雾**——你能判断即将出现、却还无法固定下来的决定和调查的模糊视图，因为它们依赖仍未开放的问题。解决一张工单会清除前方的迷雾，将现在可以明确的内容转为新的工单——一次一张，直到通往目的地的道路清晰且不再有工单。

地图的 **Not yet specified** 部分用于写下这种模糊视图：疑似的问题、之后要重新查看的区域。它是**朝向**目的地、尚未被发现的 frontier——这里的一切都在范围内，只是还不够明确，无法建立工单。按视野所允许的程度随意或完整地书写；它同时也是协作者了解工作方向的路标。

**迷雾还是工单？** 判断标准是你现在能否准确陈述问题，而**不是**你现在能否回答它。

- **在以下情况下建立工单**：问题已经明确——即使它被阻塞、暂时还无法处理。
- **在以下情况下写入 Not yet specified**：问题还无法被如此准确地表述。不要预先把迷雾切成工单大小的碎片：它比工单更粗粒度，等 frontier 到达时，一块内容可能转为多张工单，也可能一张都不转。

**Not yet specified** 不包括已经决定的内容（Decisions so far）、已经存在的活动工单，以及范围之外的内容（下一节）。

## 范围之外

迷雾只会**朝向**目的地聚集。目的地确定了范围，因此超出它的工作属于**范围之外**——它不是迷雾，也不应放在 **Not yet specified** 中。地图上有独立的 **Out of scope** 部分，用于记录你有意识地排除在**本次**工作之外的内容。范围，而不是明确程度，决定内容是否进入这里。

范围之外的工作永远不会转为明确内容——frontier 在目的地处停止——所以只有重新绘制目的地时它才会回来，并且会作为一项全新的工作，而不是继续原工作。

将某项内容排除在范围之外是范围界定行为，而不是路线上的一步。当一张已经存在的工单后来被证明位于目的地之外——可能是在绘图时错误纳入，也可能是在解决问题时暴露——**关闭它**（关闭的工单明确不在 frontier 上），并在 **Out of scope** 部分留下一行：概述它为何超出范围，并链接已关闭的工单。它不会出现在 **Decisions so far** 中，因为那里记录的是实际走过的路线——范围边界不是路线上的一步。

## 调用

有两种模式。无论哪种模式，**每个会话绝不能解决超过一张工单**——research 工单除外。

### 绘制地图

用户以一个模糊想法发起调用。

1. **命名目的地。** 使用 `grilling` 和 `domain-modeling` 两个 skill，明确这张地图要走向什么——规格说明、决定或变更。目的地确定范围，因此必须先确定。
2. **绘制 frontier。** 再次进行 grilling，这次采用**广度优先**：横向覆盖整个空间，而不是在单个线程上深入，找出开放的决定以及当前可以采取的第一步。**如果没有发现迷雾**——通往目的地的路已经清晰，整个旅程小到一个会话即可完成——就不需要地图。停下并询问用户希望如何继续。
3. **创建地图**（标签为 `wayfinder:map`）：填写 Destination 和 Notes，Decisions-so-far 留空，在 **Not yet specified** 中勾勒迷雾。
4. **创建现在能够明确的工单**，将其作为地图的子 issue——然后在**第二遍**建立阻塞边（issue 需要先有 id，之后才能相互引用）。建立关系会将它们分入 frontier 或阻塞区；尚无法明确的内容全部留在迷雾中的 **Not yet specified** 部分。
5. **启动 research subagents。** 对刚创建的每张 `research` 工单，启动一个使用 `research` skill 的 subagent 并行解决，在临时的 `research/<name>` 分支上记录发现，并从工单添加上下文指针。
6. 停止——绘图是一个会话的工作；不在此处亲自解决任何工单。

### 沿地图推进

用户通过地图（URL 或编号）发起调用。工单是**可选的**——没有指定工单时，由你选择下一项决定，而不是用户选择。

1. 加载**地图**——加载低分辨率视图，而不是每张工单的正文。
2. 选择工单。如果用户指定了某张，就使用它。否则按顺序取第一张 frontier 工单。**认领它**：在任何工作之前先将它分配给自己。
3. 解决它——**按需放大查看**：按需获取任何相关或已关闭工单的完整正文；调用 `## Notes` 区块中列出的 skills。如有疑问，使用 `grilling` 和 `domain-modeling`。
4. 记录解决结果：将答案作为**解决评论**发布，**关闭** issue，并向地图的 Decisions-so-far 追加上下文指针。
5. 添加新出现的工单（先创建，再建立关系）；将答案使其变得明确的迷雾转为工单，清除 **Not yet specified** 中对应的每一块，使其只存在于新的工单中。如果答案显示某张工单——无论是当前工单还是其他工单——位于目的地之外，就将其**排除在范围之外**，而不是在路线中解决它。如果该决定使地图的其他部分失效，就更新或删除那些工单。

用户可能会并行处理未阻塞的工单，因此要预期其他会话会同时编辑 tracker。
