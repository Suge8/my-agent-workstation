此 skill 会利用当前对话上下文和对代码库的理解来生成规格说明。不要访谈用户——只需综合你已经知道的信息。

议题跟踪器和分诊标签的词汇应该已经提供给你；如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 探索代码仓库以了解代码库的当前状态（如果你还没有这样做）。在整个规格说明中使用项目领域术语表中的词汇，并遵循你正在修改的区域中的 ADR。

2. 勾勒出你将在哪些接缝处测试该功能。应优先使用已有接缝，而不是新建接缝。尽可能使用最高层级的接缝。如果需要新接缝，应在能达到的最高层级提出。跨越代码库的接缝越少越好——理想数量是一个。

向用户确认这些接缝是否符合他们的预期。

3. 使用下面的模板编写规格说明，按跟踪器的发布前查重约定处理与他人工单的重叠后，再发布到项目议题跟踪器。只挂 `spec` 类型标签（实际字符串见分流标签表）；spec 是容器，不打分诊标——可领的是它拆出的工单，进度由子 issue 计数派生。

<spec-template>

## 问题陈述

从用户角度描述用户遇到的问题。

## 解决方案

从用户角度描述问题的解决方案。

## 用户故事

一份很长的编号用户故事列表。每个用户故事应采用以下格式：

1. 作为一名<角色>，我希望拥有一项<功能>，以便<收益>

<user-story-example>
1. 作为一名移动银行客户，我希望查看我的账户余额，以便更明智地决定如何消费
</user-story-example>

这份用户故事列表应极其全面，涵盖该功能的所有方面。

## 实现决策

列出已经做出的实现决策。其中可以包括：

- 将要构建/修改的模块
- 将要修改的模块接口
- 开发者提供的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体文件路径或代码片段。它们可能很快就会过时。

例外：如果原型生成的代码片段比文字更精确地表达了某项决策（状态机、reducer、schema、类型形状），可以将其内联到相关决策中，并简要注明它来自原型。只保留与决策直接相关的部分——不要放入可运行的演示，只放入重要内容。

## 测试决策

列出已经做出的测试决策。包括：

- 对优秀测试的描述（只测试外部行为，而不是实现细节）
- 将要测试的模块
- 测试方面的既有实践（即代码库中类似类型测试的先例）

## 范围外

描述本规格说明不涵盖的事项。

## 进一步说明

关于该功能的任何其他说明。

</spec-template>
