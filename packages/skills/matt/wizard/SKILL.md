# Wizard

**向导**是一个 bash 脚本，一步一步带人走完某个手动流程——那种手工做很烦、每次还要重新讲给 AI 听的流程。它会打开每个 URL，明确说出该点什么、复制什么，接住这些值，写到它们该去的地方（`.env`、GitHub secrets），每一步都确认，并显示还剩几个阶段。它可能用来配置第三方服务、执行一次性迁移，或把项目从一个状态搬到另一个状态。

令人愉悦的交互体验已经由 [template.sh](template.sh) 解决——逐阶段进度、确认关卡、跨平台打开 URL（含 WSL）、隐藏式密文输入、幂等的 `.env` 更新写入、`gh secret`/`gh variable` 写入，以及收尾摘要。**你的工作只是划定流程范围并编写它的各个阶段。** `STAGES` 标记以上的库代码在每个向导中完全相同；这种一致性正是重点——绝不要手工修改它。

向导默认是一次性的——为一次运行而造，存到 scratch 或 `scripts/` 路径，事情做完就删。只有当用户希望仓库里长期保留一条可重复的配置路径时，才提交它。

## 流程

### 1. 划定流程范围

弄清人类必须执行的每一个手动步骤，以及沿途会拿到的每一个值。先读仓库，不要空着问：

- 配置类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一处 `secrets.*` / `vars.*` 引用都是向导必须产出的值）。
- 迁移或状态切换类：当前状态、目标状态，以及两者之间不可逆的动作。

然后把有序的阶段清单和每个阶段产出的值展示给用户确认——他们可能增加、删除或重排。

**完成标准：** 每个阶段都已按顺序命名；对每个被捕获的值，你都知道（a）人类从哪里拿到它，（b）它被写到哪里（`.env`、GitHub secret、两者都写，或哪都不写——有些阶段是纯动作），（c）它是否为密文（需隐藏式输入）。

### 2. 铺开每个阶段的路径

为每个阶段写出人类要走的精确路径：打开哪个 URL、在那里做什么、值显示在哪里、它填进哪个变量——例如“Dashboard → Developers → API keys → Reveal test key → 复制”。凡是你并不确知当前 UI 或确切命令的地方，直说，并询问用户或查文档——绝不要编造可能不存在的步骤。

**完成标准：** 每个阶段都能落到一个陌生人也能照做的具体指令。

### 3. 编写向导

把 `template.sh` 复制到目标路径。用一个 `stage` 对应一个步骤替换示例阶段，按依赖顺序排列。使用库里的辅助函数——`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`——并把 `TOTAL_STAGES` 设为你写的阶段数。

守住模板设定的标准：先打开 URL 再索取它的值，任何密文用 `ask_secret`，每个需要留存的值都 `write_env`，只对 CI 真正需要的值用 `set_secret`，任何不可逆动作之前先 `confirm`。每个 `stage` 都会清屏，只显示当前步骤——所以一个阶段只承载一件专注的事，别让人类需要的信息被滚走。不要碰标记以上的库代码。

### 4. 验证并交付

- `bash -n <script>`；有 `shellcheck` 就跑一遍。
- `chmod +x <script>`。
- 不要自己端到端跑它——它会打开浏览器并阻塞等待人类输入。改用静态走查：第 1 步列出的每个值都被捕获、并落到第 1 步所说的位置，且每个 `set_secret` 的名称与 CI 中的 `secrets.*` 引用完全一致。
- 告诉用户怎么运行它。如果它是一条可重复的配置路径，就提交它并从 README 链接过去，让下一个人去跑脚本，而不是再问一次 AI。
