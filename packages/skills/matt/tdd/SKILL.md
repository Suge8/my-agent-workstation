# 测试驱动开发

TDD 是红 → 绿循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好的测试、测试放在哪里、反模式，以及循环规则。每个循环都适用每个章节——在循环前和循环中查阅，而不是事后查阅。

探索代码库时，阅读 `CONTEXT.md`（如果存在），使测试名称和接口词汇与项目的领域语言一致，并遵守你正在修改区域中的 ADR。

## 什么是好的测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变；测试不应如此。好的测试读起来像规格说明——“用户可以使用有效购物车结账”明确说明了存在什么能力——并且能够经受重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝——测试放在哪里

**接缝**是你进行测试的公共边界：在不深入内部的情况下观察行为的接口。测试位于接缝处，绝不针对内部实现。

**只在事先约定的接缝处测试。** 编写任何测试前，写下要测试的接缝并与用户确认。未经确认的接缝不得编写测试。你不可能测试一切——提前约定接缝，才能让测试精力落在关键路径和复杂逻辑上，而不是每个边界情况上。

询问：“公共接口是什么，以及我们应该测试哪些接缝？”

当接口的形态本身存在疑问——模块应有多深、接缝属于哪里、接口应暴露什么——使用 `codebase-design` skill 的词汇。它是 module、interface、depth、seam、adapter、leverage 和 locality 这些术语的共享来源，是供查阅的参考，而不是要运行的会话。

## 反模式

- **与实现耦合**——mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。表现是：重构后行为没有变化，但测试却失败。
- **同义反复**——断言按照代码的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以相同方式手工推导的快照、断言常量等于自身），因此测试按构造就能通过，永远无法与代码产生分歧。期望值必须来自独立的真值来源——已知正确的字面值、完整示例或规格说明。
- **水平切片**——先编写所有测试，再编写所有实现。批量测试验证的是_想象中的_行为：测试的是事物的_形状_而不是面向用户的行为，测试会对真实变化不敏感，并且在理解实现之前就确定了测试结构。应改为**垂直切片**——一个测试 → 一个实现 → 重复；每个测试都是一枚**示踪弹**，响应上一个循环带来的认识。

## 循环规则

- **先红后绿。** 先编写失败测试，然后只写足以使其通过的代码。不要预判未来测试，也不要添加推测性功能。
- **一次一个切片。** 每个循环包含一个接缝、一个测试和一个最小实现。
- **重构不属于循环。** 重构属于评审阶段（见 `code-review` skill），而不是红 → 绿实现循环。
