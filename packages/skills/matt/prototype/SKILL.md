# 原型

原型是**回答一个问题的一次性代码**。问题决定形式。

## 选择分支

确定要回答哪个问题——根据用户提示、周边代码，或在用户在线时询问：

- **“这个逻辑 / 状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的 HTML 文件——包含自由操作按钮和带标签页的引导式演练——推动状态机经过那些在纸面上难以推理、且非开发者可以操作的案例。
- **“它应该看起来怎么样？”** → [UI.md](UI.md)。在单一路由上生成多个截然不同的 UI 变体，通过 URL search param 切换，并使用底部浮动栏。

两个分支产出的工件截然不同——选错会浪费整个原型。如果问题确实含糊且联系不到用户，就默认选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 适用于两者的规则

1. **从第一天起就是一次性的，并明确标记为一次性。** 将原型代码放在实际使用位置附近（紧挨着它所原型化的模块或页面），让上下文显而易见——但命名时要让随手阅读的人看出它是原型而不是生产代码。对于一次性 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **运行必须简单。** UI 原型从项目 task runner 中的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击即可打开的单个 HTML 文件。无论哪种方式，都不需要思考如何启动。
3. **默认不持久化。** 状态保存在内存中。持久化正是原型要检查的事情，不应成为依赖。如果问题明确涉及数据库，则使用临时数据库或本地文件，并使用清晰的 “PROTOTYPE — wipe me” 名称。
4. **跳过打磨。** 不要测试，不要超出让原型**可运行**所需范围的错误处理，不要抽象。重点是快速学到东西。
5. **展示状态。** 每次 action 后（逻辑）或每次变体切换时（UI），打印或渲染全部相关状态，让用户看见发生了什么变化。
6. **完成后记录。** 将经过验证的决策纳入真实代码，然后将原型本身作为**主要来源**记录：提交到一次性分支，而不是主分支，并在实现 issue 上留下指向该分支的上下文指针。同时记录答案——结论以及它解决的问题——放入 issue 或一次 commit 中。主分支只保留经过验证的决策。
