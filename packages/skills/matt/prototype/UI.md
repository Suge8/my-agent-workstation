# UI 原型

在单一路由上生成**多个截然不同的 UI 变体**，通过底部浮动栏切换。用户在浏览器中切换变体，选定一个（或从每个变体中借用一些部分），然后丢弃其余部分。

如果问题关于逻辑/状态，而不是某个东西看起来如何——这是错误的分支。使用 [LOGIC.md](LOGIC.md)。

## 适合这种形式的场景

- “这个页面应该看起来怎么样？”
- “在确定之前，我想先看看这个 dashboard 的几个选项。”
- “为设置页面试试不同布局。”
- 任何用户本来会花一天时间，在脑中于三个模糊 mockup 之间选择的情况。

## 两种子形式——强烈优先选择子形式 A

当 UI 原型**紧贴应用其余部分**时，更容易判断——真实的 header、真实的 sidebar、真实的数据、真实的密度。独立的一次性路由是个真空：每个变体单独看都不错。只要有合理的现有页面可以承载变体，就默认使用子形式 A。只有当原型确实没有附近的归宿时，才使用子形式 B。

### 子形式 A——调整现有页面（首选）

路由已经存在。变体**在同一路由上**渲染，通过 `?variant=` URL search param 控制。现有的数据获取、params 和 auth 全部保留——只有渲染发生切换。这是默认选择；除非有具体理由，否则使用它。

如果原型针对的东西还没有页面，但*自然会放在某个页面里*（dashboard 的新区域、设置页面上的新卡片、现有流程中的新步骤），这仍然属于子形式 A。将变体挂载到宿主页面中。

### 子形式 B——新页面（最后手段）

只有当原型的东西确实没有任何现有页面可以承载时才使用——例如全新的顶层界面，或无法合理嵌入其他位置的流程。

遵循项目已有的路由约定创建一个**一次性路由**——不要发明新的顶层结构。命名时要让它明显是原型（例如在路径或文件名中包含 `prototype`）。使用同样的 `?variant=` 模式。

确定使用子形式 B 之前，先确认：真的没有现有页面可以嵌入它吗？空路由会掩盖真实数据页面能够暴露的设计问题。

两种子形式的底部浮动栏完全相同。

## 流程

### 1. 明确问题并选择 N

默认使用 **3 个变体**。超过 5 个就不再是截然不同，而会变成噪音——上限为 5 个。

在原型所在位置或文件顶部注释中用一行写下计划：

> “设置页面的三个变体，通过 `?variant=` 切换，位于现有的 `/settings` 路由上。”

无论用户是否在线提出异议，这都有效。

### 2. 生成截然不同的变体

起草每个变体。每个变体都必须符合：

- 页面目的及其可访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、普通 CSS 等）。
- 清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**——布局、信息层级、主要操作方式都不同，而不只是颜色不同。三个略微调整的卡片网格不是 UI 原型，而是墙纸。如果两个草案过于相似，就用明确的“不要使用卡片网格”指导重做其中一个。

### 3. 将它们连接起来

在路由上创建一个切换器组件：

```tsx
// 伪代码——根据项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形式 A（现有页面）：保留切换器上方现有的全部数据获取；只有渲染的子树根据变体改变。

对于子形式 B（新页面）：一次性路由位于 `/prototype/<name>` 下，并挂载同一个切换器。

### 4. 构建底部浮动切换器

在屏幕底部居中的小型固定栏，包含三部分：

- **左箭头**——切换到上一个变体（循环）。
- **变体标签**——显示当前变体 key，如果变体导出了名称，也显示该名称。例如 `B — Sidebar layout`。
- **右箭头**——切换到下一个变体（循环）。

行为：

- 点击箭头更新 URL search param（使用框架的 router——Next 使用 `router.replace`，React Router 使用 `navigate` 等），使变体可分享且重载后保持。
- 键盘：`←` 和 `→` 箭头键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截箭头键。
- 在视觉上与页面区分开（例如高对比度胶囊、细微阴影），让人明显知道它不属于正在评估的设计。
- 在 production 构建中隐藏——通过 `process.env.NODE_ENV !== 'production'` 或等效检查控制，避免一次误合并就把栏发布给用户。

将切换器放入一个单独的共享组件中，以便两种子形式复用。放在项目的共享 UI 所在位置。

### 5. 交付

提供 URL（以及 `?variant=` key）。用户会在方便时切换浏览。常见的有价值反馈是“我要 B 的 header 加上 C 的 sidebar”——这才是他们真正想要的设计。

### 6. 记录答案并清理

某个变体胜出后，记录答案——哪个变体以及为什么——然后按照 [SKILL](SKILL.md) 的描述记录原型。将胜者纳入真实代码，其余部分移到一次性分支，而不是主分支：

- **子形式 A**——将胜者纳入现有页面；从主分支删除落选变体和切换器。
- **子形式 B**——将胜者提升为真实路由；从主分支删除一次性路由和切换器。

完整的变体集合是主要来源，因此应该落在一次性分支而不是垃圾桶中——变体组件和切换器留在主分支会迅速腐烂，并让下一个读者困惑。

## 反模式

- **变体只在颜色或文案上不同。** 那是调整，不是原型。真正的变体在结构上存在分歧。
- **在变体之间共享过多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了目的。每个变体都应该可以自由抛弃布局。
- **将变体连接到真实变更。** 只读原型没有问题。如果变体需要变更，就指向 stub——问题是“它应该看起来怎么样”，而不是“后端是否正常工作”。
- **直接将原型提升到生产环境。** 变体代码是在原型约束下编写的（没有测试、错误处理极少）。纳入真实代码时要正确重写。
