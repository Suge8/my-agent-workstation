# 逻辑原型

一个单文件、自包含的 HTML 文件——一个**可分享的演示**——让任何人都能通过点击按钮驱动状态模型。当问题涉及**业务逻辑、状态转换或数据形状**时使用它——这类东西在纸面上看起来合理，但只有经过真实案例才会感觉不对。

因为它只有一个文件且无需安装，你可以把它交给非开发者——设计师、PM、领域专家——让他们亲自感受这个模型。所以它使用他们的语言，而不是代码的语言。

## 适合这种形式的场景

- “我不确定这个状态机是否能处理 X 后 Y 这种边界情况。”
- “这个数据模型真的能表示……这种情况吗？”
- “我想在编写 API 之前，先亲手感受一下它应该是什么样。”
- 任何有人想要**按下按钮并观察状态变化**的情况。

如果问题是“它应该看起来怎么样”——这是错误的分支。使用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

写代码之前，写下你要原型化的状态模型和问题。在演示顶部写一段话（放在可见的介绍中，而不只是注释里）。回答错误问题的逻辑原型纯属浪费——明确问题，之后才能检查，无论用户现在正在观看，还是离开电脑（AFK）后再回来。

### 2. 将逻辑隔离到可移植模块中

将实际逻辑——回答问题的那部分——放在一个单独的 `<script>` 块中，写成一个小型纯模块，之后可以从中提取并放入真实代码库。周围的页面是一次性的；这个模块不是。

合适的形式取决于问题：

- **纯 reducer**——`(state, action) => state`。适合 action 是离散事件且 state 是单个值的情况。
- **状态机**——明确的状态和转换。适合“当前哪些 action 甚至是合法的”本身就是问题的一部分。
- **一小组**作用于普通数据类型的纯函数。适合没有隐式当前状态、只有转换的情况。
- **具有清晰方法表面的类或模块**，适合逻辑确实拥有持续内部状态的情况。

选择最符合所提问题的形式，*而不是*最容易接到页面上的形式。保持纯粹：不要有 DOM，不要有 `document`，不要让按钮处理器深入其内部。页面调用它；没有任何东西反向流入页面。这正是原型能超越自身生命周期而继续有用的原因：问题回答之后，经过验证的 reducer / machine / function set 可以自行提取到真实模块中。

### 3. 构建可分享的 HTML 文件

一个文件，使用普通 HTML/CSS/JS——不要框架，不要 bundler，不要 server；所有内容都内联，以便双击打开，也能经由电子邮件传来传去。任何人打开它就应该能运行。

为非开发者编写。每个标签都使用**领域语言**，而不是代码——按钮和状态读起来应该像业务，而不是 reducer。用通俗的话解释正在发生什么。

按从上到下的清晰层级布局：

1. **标题和一行说明**，说明这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**——将全部相关状态渲染为可读面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，以便看见变化。在有助于非开发者理解的地方，指出刚刚发生了什么变化。
3. **自由操作按钮**——每个 action 一个按钮，始终可用，让任何人都能按任意顺序试探模型。每次点击都会 dispatch 它的 action 并重新渲染状态。
4. **引导式演练**——一组**场景**，每个标签页一个。每个标签页包含一段简短的通俗场景描述——它设置的情境以及要观察的内容——下面是该场景中按顺序需要**按下的按钮**。每一步都是真实按钮：点击后执行该 action 并移至下一步。开始演练时重置为已知初始状态，确保场景每次都以同样的方式运行。

选择能展示棘手案例的场景——正常路径、复杂边界情况、尝试执行本应非法的操作——这些是在纸面上难以推理的情况。

保持美观但克制：清晰的排版、宽松的间距、一种强调色。不要动画，不要噱头——不要让任何东西与状态和按钮争夺注意力。

### 4. 交付

把文件发给他们，或为他们打开。他们会在方便时点击演练和自由操作；有趣的时刻通常是他们说“等等，这不应该是可能的”或“嗯，我以为 X 会不一样”——这些就是**想法**中的 bug，而这正是全部目的。如果他们想要新的 action 或场景，就添加它们。原型会不断演进。

### 5. 记录答案和原型

原型回答问题后，先记录答案，再按照 [SKILL](SKILL.md) 的描述记录原型。逻辑专属的对应方式是：经过验证的 reducer / machine / function set 提取到真实模块中（决策被吸收）；HTML 外壳则随同保留原型的临时分支一起保存，作为主要来源——而且它是单个自包含文件，因此在那里仍然可以轻松重新运行。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型。
- **不要接入真实数据库。** 除非问题明确涉及持久化，否则使用内存状态。
- **不要泛化。** 不要考虑“以后如果我们想支持 X 怎么办”。原型只回答一个问题。
- **不要混淆逻辑和页面。** 如果纯模块引用 DOM、`document` 或按钮处理器，它就无法再被提取。让页面成为纯模块之上的薄壳。
- **不要使用框架、bundler 或 server。** 接收者应该双击一个文件即可运行；React 应用或开发服务器会破坏“可分享”这一点。
- **不要把 HTML 外壳交付到生产环境。** 页面针对手动点击操作进行了优化。背后的逻辑模块才是值得保留的部分。
