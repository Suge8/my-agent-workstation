# Set Test Chain

目标：让 Agent 能独立、重复地证明行为和静态质量门正确，同时让测试代码保持精简。

## 先分流

只走一个主分支：

1. 已知 bug、错误输出、性能回归或 flaky，需要复现、定位和修复 → **Diagnosing Bugs**。本 Skill 不做根因排查；Diagnosing Bugs 产出的回归用例通过下文价值门后进入现有验证链。
2. 项目没有合格验证链 → **首次建链**。
3. 改动行为已有有价值的用例覆盖，或改动是纯重构、改名、格式化等无行为变化 → **只运行受影响验证**，不新增用例。
4. 新增或改变的行为通过测试价值门，但没有覆盖 → **补覆盖**。
5. 行为不值得持久测试 → **不写测试**；运行已有静态门，必要时做一次性取证，不记伪测试债。
6. 值得持久测试，但自动化碰不到 → **取证兜底并记录测试债**。

## 测试价值门

持久测试必须同时满足：

- 保护用户可观察行为、公共合同或高风险业务不变量；
- 一种可信回归会让它失败，不是在重证语言、框架或常量本身；
- 该合同没有被现有测试、类型系统、编译器或 lint 等价保证；
- 使用稳定 seam，不依赖私有调用、mock 接线、偶然 DOM、固定话术或夹具巧合；
- 防回归收益高于运行、理解和维护成本。

不满足就不写。禁止以覆盖率、测试数量或“每个函数一条”为目标。纯函数、解析器、状态转换和边界条件若能低成本保护真实合同，仍适合单元测试。

## 清理低价值测试

只要本次会修改测试文件，完成前必须检查该文件和同一行为的相邻用例。发现以下测试就一并清理：

- 重复另一条测试的同一合同，没有增加边界或风险信号；
- 只测 getter、常量、函数名、框架能否渲染或“没崩”；
- mock 什么就断言什么，未经过真实生产数据流；
- 锁死私有调用次数、内部结构、无业务语义的快照或文案；
- 已被类型系统、编译器或静态规则完整保证。

删除前先说明它声称保护的合同：若合同有价值且别处已覆盖，保留信号最强的一条；若有价值但没有覆盖，替换成一条最近正确 seam 上的行为测试；若没有值得保护的合同，直接删除。删除后运行最窄受影响验证，不降低断言、不关闭规则、不调整覆盖率阈值来掩盖删除。

默认只清理本次测试文件和同一行为的直接相邻用例；全仓测试瘦身必须由用户明确要求，避免把局部任务扩成无界审计。

## 首次建链

先检查现有依赖、测试入口、package/task scripts、CI 和 1–3 个相邻项目模式。合格验证链应满足：

- Agent 可独立运行，不需要人肉点击；
- 无头或隔离运行，不抢用户的输入设备；
- 结果可重复，不依赖 sleep、实时网络或执行顺序；
- 测试断言具体且通过价值门，不是“没崩就算过”；
- 仓库已配置的 formatter check、lint、typecheck/compile 已接入可重复入口。

按 [references/toolchains.md](./references/toolchains.md) 选择项目已有生态中的最小方案；只有项目内没有事实源且 API 或选型不确定时，才查当前官方资料。普通建测试任务不新增 formatter、linter 或 Hook；用户明确要求新建静态质量门时，才选一套最小工具并说明新增开发依赖。默认不新增生产依赖。

最小交付只有两部分：一个可运行的验证入口，以及当前最需要的一条有价值行为用例。不要一次铺完整套件。

首次校准必须证明测试信号真实：

1. 运行持久 harness 的正式入口，positive control 必须 exit 0；命令不存在、导入错误或 0 tests 都不算通过，先修入口并重跑至绿。
2. 在同一持久测试文件里临时反转一条断言，再运行同一 harness 入口，确认测试进程非零退出并报告预期失败；inline 一次性脚本或无关失败不算校准。
3. 精确还原该断言，再运行同一入口至全绿。

完成门：工具轨迹必须按顺序出现“同一 harness 绿 → 断言反转 → 红 → 断言还原 → 绿”。禁止用测试框架常识或口头声明替代实际运行。negative control 只校准测试 harness，不得修改业务代码制造 bug，也不得留在工作区。

校准是 harness 的一次性成本：只在新建或大改 harness 入口时执行；harness 已校准过的项目，后续补覆盖和日常改动直接跑受影响验证，不得重复红绿红流程。静态门不需要反转规则校准。

## 已有链补覆盖

1. 读本次行为变化、现有验证入口和 1–3 个相邻用例；先搜现有用例和静态门是否已保证该合同。
2. 先过测试价值门；不通过就不新增用例。
3. 通过时，在最近的正确 seam 增加一条行为断言。覆盖粒度按行为不按 diff：同一行为的多处修改共用一条用例，不为每个改动点各写一条。
4. 按“清理低价值测试”处理触及范围，再运行最窄受影响验证；接口或配置变化时再跑对应上层验证。
5. 报告具体命令、通过数量，以及删除或拒绝新增测试的理由。

这里**不要求先出现失败测试**。新增的正常行为可能已经实现，补上的测试第一次运行就通过是合法结果；不得为了套红绿流程临时写错断言。若测试暴露真实缺陷，转 Diagnosing Bugs 复现和定位。

## 静态质量门

静态门是验证链的一部分，但不能代替行为测试：

1. 从项目配置和现有 scripts 识别 formatter check、lint、typecheck/compile；日常验证只运行已有命令，未配置则跳过，不修改验证配置。
2. 只有用户明确要求首次建链，且仓库缺少统一入口时，才把已有静态门接入一个最小入口。
3. 验证使用不改文件的 check 模式。自动修复命令可用于修复，但不能作为通过证据。
4. 沿用项目现有工具和规则，不为追新迁移，不并装功能重复的两套工具。快速入口不放耗时 E2E、全量构建或发布检查。

Git Hook 只是本地加速器，不是事实源，因为可以被跳过且可能未安装。已有 Hook 就让它调用同一个快速验证入口；只有用户明确要求且仓库已有稳定快速入口时才新建 Hook。Husky 只用于已采用 Node 工具链的项目，不作为跨语言默认依赖；Hook 内禁止放慢速或不确定的 E2E。CI 或可手动运行的统一命令始终保留。

## 自动化够不到时取证

按接近用户真实路径的顺序选最短方法：

1. **flow-browser-use**：页面、DOM、截图、console、network；
2. curl 或 CLI：直接调用并断言响应内容；
3. 带具体断言的日志；
4. **better-computer-use**：桌面应用或真机兜底，读取控件并截图；
5. 都不可行：给用户“打开哪里 → 做什么 → 应看到什么”的最短清单，明确标注未验证。

证据必须来自本次执行。只有通过测试价值门且值得长期保护的缺口才记录测试债；同一路径第二次需要人工取证时，应转成建链任务。

## 质量红线

- 快：最窄验证应快到每次改动都愿意运行。
- 确定：固定 seed、时钟和网络；用条件等待，不用 sleep。
- 精确：一条用例验证一个行为，失败信息能直接定位合同。
- 精简：每条持久测试都通过价值门，无重复静态门的伪覆盖。
- 干净：无永久 skip、临时错误断言、僵尸进程或测试生成物。
