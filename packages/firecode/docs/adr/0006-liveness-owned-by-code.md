# 委派闭环的活性归代码，模型只保留决策权

2026-08-16 夜跑实测：工人交活后，指挥官把后续指令写进给用户的回复而没有实际投递，
流程停摆 1.5 小时直到用户开口——凡是靠模型记忆承担的活性，规模化并行下必然失守。
据此决定：结果送达后"必须有人处置"由插件保障，处置什么仍由指挥官决策。落定类事件（工人结果、中断、审查终态、自动续跑提醒）
要求指挥官在该回合内处置（send / review / stop / hold 之一）；未处置则在回合结束时注入
一次可见提醒，再不处置升级为用户通知，不再追加。工人被中断（esc 或连接异常）不按执行失败
回传，插件续监其动静：用户接手则结果照常回流，五分钟无人接手则提醒指挥官续派。
处置标记与中断时刻随工人档案持久化，reload 后重挂。

## 考虑过的选项

心跳/定时巡检被否：idle 本身不是异常（等用户决策的 idle 是正常态），"收到结果却未处置"
才是，而后者在回合边界即可确定性判定，轮询只会制造误报。加码系统提示词纪律被否：
指挥官自订的"回复前先核对"纪律已实战失守两次。同步化子代理（结果作为工具返回值）被否，
见 ADR-0005。五分钟到点由插件代发"继续"被否：委派文本归模型，插件盲续会复活指挥官
明知已作废的任务。
