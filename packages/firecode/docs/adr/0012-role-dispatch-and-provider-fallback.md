# 角色化派发与故障限定 fallback

Master 以 `master.roles` 对象配置角色表。角色名固定为调研员、工程师、全栈、架构师、设计师、哨兵六个词，配置可启用其中任意非空子集；每个键以 `provider/model/thinking` 原子绑定主模型与思考档，可声明至多两个有序 fallback 原子，同一模型可供多个角色复用。`subagents` 的 role 参数只接受六个固定词，start 必须按已配置角色派发，send 可按已配置角色切换，thinking 只作为显式覆盖；裸 model 参数、旧 `{ model, thinking }` 配置与未发布的 `master.models` 角色数组均不识别。

fallback 只处理供应商基础设施故障：额度或计费耗尽、模型不可用或找不到，以及宿主完成既有退避重试后仍持续出现的 5xx。瞬时限流继续由宿主处理，任务失败与质量问题交给指挥官裁决。触发后，Worker 在原会话中切换到链中下一原子并继续，档案记录实际模型且不自动切回；切换事件明示前后原子与原因，链用尽明确报错。

Worker 档案随角色字段升级为 v8。v7 池沿用既有旧状态规则丢弃并从空池重建，不增加迁移或兼容分支。

替代方案包括继续让指挥官逐次选择模型、按任意失败自动换模、由宿主统一跨供应商 fallback，以及为旧参数保留兼容层。逐次选模重复消耗决策注意力；任意失败换模会把质量路由伪装成容灾；宿主不了解 FireCode 角色与档案事实；兼容层会形成第二套派发语言。因此均不采用。

## 后果

派发语言稳定为六个固定职业角色，模型与默认思考档成对配置，提示词只列出当前已配置角色并可直接基于职责选择。供应商确定性故障可在无人值守时继续推进，同时每次降级都进入事件流。代价是配置升级后旧写法立即拒绝启动，旧池无法恢复；fallback 也不会掩盖限流、任务失败或质量不足，链用尽时仍需用户或指挥官处理。
