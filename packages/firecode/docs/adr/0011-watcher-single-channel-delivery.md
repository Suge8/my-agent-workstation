# 观察员收束为单通道

观察员的评估结果不再分 nit / concern / blocker 三档，只剩说与不说两态：说了就是一条带 `<firecode_watcher>`
信封的普通消息，经与子代理结果完全同构的宿主队列投递——指挥官忙时在当前回合的句缝追加，空闲时唤起一个
回合，Esc 打断后照发。开口门槛移进提示词：只有当这条话此刻送达会改变指挥官下一步动作时才开口。

三档的设计假设是"按严重度选择打扰强度"，实测站不住。`concern` 渲染成卡看似已经插话，实际不唤起回合，
主模型要等用户下次开口才看见，纠偏严重滞后——用户看到的回复未经提醒。`nit` 只出事件卡，从不进入模型
上下文，即没有行为消费者：唯一的读者是人，而人本来就在看会话本身。剩下的 `blocker` 才是真正要的语义，
于是 severity 字段在删掉两档之后没有任何分支还读它，作为僵尸字段退役而不是留作"以后可能有用"。

代价是唤醒成本：每次开口都可能唤起一个回合，包括用户 Esc 打断后的现场。这换来零特殊分支——投递时机的
判断只有宿主队列一个事实源，插件侧不再维护中断跟踪与空闲探测这类会与宿主漂移的状态。极少数情况下 Esc
后的发言会重启一个回合，接受；相比之下静默丢弃重要纠偏的代价更高。打扰频率改由提示词门槛控制：模型判断
"此刻送达是否改变下一步动作"，比机器按档位猜打扰强度更贴近真实需要。

## 后果

Bark 钩子随之删除——手机通知只来自会话本身的通知职责，观察员不再是独立的推送来源。展示只剩一种样式，
无档位配色；`advise` 工具只收 `note`。
